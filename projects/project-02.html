Project 2: AI Trading Agent — RL + Zones

A scientific test of whether a reinforcement-learning trader that understands price zones, price action and market regime generalizes better than one trained on raw price bars, using S&P 500 (SPY) 5-minute data from 2015–2021.

Status: active · early stage Started Aug 15, 2026 Last updated Oct 28, 2026

Central hypothesis

A zone-aware, price-action-driven, regime-conditioned RL system with specialized entry and an unrestricted exit policy may generalize better than an RL system trained directly on raw bars.

It is treated as a hypothesis to be tested, not an assumption. The goal is not to maximize backtest profit but to determine whether a robust, generalizable edge exists at all.

Goals & objectives

Test the hypothesis fairly

Compare zone/price-action/regime RL against a raw-bar RL control under an identical protocol, step by step (roadmap Steps 19–26).

Separate entry from exit

Find out whether entry or exit is the bottleneck, then test specialized entry and position-management agents against a single monolithic policy.

Prove it survives scrutiny

Walk-forward validation, purging and embargo, cost and delay stress, falsification tests, cross-asset checks and a locked final out-of-sample set before any paper trading.

Research findings

What was established

  • A review of the predecessor RL project identified what to reuse and what had already been disproven. Its environment, risk manager, backtester, metrics, leakage registry, baselines and splits were ported unchanged.
  • The new PyTorch pipeline reproduces the predecessor's known failure modes and fixes, which is good evidence the port is behaviorally correct.
  • One real bug was found and fixed: Sharpe and Sortino returned ~1016 on a constant return series because of an exact-zero check on floating-point noise.

Current methods

  1. Simulator first: a Gymnasium-style trading environment with an external risk layer (stops, max trades/day, forced end-of-day flat) and realistic costs and slippage.
  2. Leakage control: every feature has a causal-availability definition, and tests mutate future bars to prove past features don't change.
  3. Baselines: 6 simple non-RL strategies run through the same execution engine.
  4. RL agent: PyTorch PPO (clipped surrogate + GAE), one trading day per episode.
  5. Tracking: every run is logged with parameters, seeds, code and data versions.

Next steps

  1. Close the raw-bar control run with a checkpointed full-scale (72-month) PPO run using dense reward.
  2. Decide whether to build DDQN first (roadmap Step 15) or document PPO-first as a deviation.
  3. Write the formal research specification (Step 1) and simulator validation report (Step 3).
  4. Add an adversarial leakage-injection test (Step 11).
  5. Build and validate the zone engine (Steps 4–5) before spending compute on zone-aware RL.

Main challenges

  • Blocker Policy collapse at full scale: too few iterations and sparse reward make PPO default to "do nothing".
  • Compute Each PPO iteration takes about 3 minutes on this data, so full runs need checkpointed resumes.
  • Reproducibility The diagnostic run wasn't logged to the tracker and must be re-run with logging.
  • Process Early infrastructure was built out of roadmap order and is being reconciled step by step.

Lessons learned

Run a small, fast diagnostic before any full-scale training run. It surfaces the same failure modes far more cheaply.

Log every run at the moment it's run, including quick diagnostics. A result that exists only in a report can't be reproduced.

Pair every safety check, like leakage detection, with an adversarial test that deliberately triggers the failure it exists to catch.

Reviewing the predecessor project first turned a confusing new failure (policy collapse) into a known, quickly diagnosed one.
